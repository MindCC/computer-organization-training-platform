# 《芯游记：街角装机店》互动剧本游戏设计

设计日期：2026-10-03。设计对象：现有装机教学系统中的经营游戏模块。

本文是新一轮游戏设计方案，角色、场景、剧情与经营系统尚未全部实现。现有客户问答、配置评估、真实 3D 装机、双内存条、桌旁立式开机与提交回执可作为制作基础。视觉概念图是方向探索；正式人物立绘、场景分层与可点击区域需要另外制作。

## 一、游戏定位

**一句话：经营一间有故事的装机店，听懂客户的需求，亲手装出适合他的电脑。**

- 类型：互动剧本 + 轻经营 + 真实 3D 装机。
- 玩家：店铺的新任店长，也是负责装机的工程师；不预设姓名、性别和外貌。
- 舞台：虚构城市青禾街，社区、学校与创业园之间的一家老店。
- 店名默认“芯邻装机”，开场可改名。
- 主线：老店师傅准备退休，玩家接手试营业。六个营业日后举办社区科技节。玩家决定店铺靠什么赢得认可。
- 体验：客户进门有声音和动作，需求通过交谈逐渐明确；装机时进入现有 3D 工作台；交付时客户带着具体反馈回来。
- 时长目标：单单 8–12 分钟，第一章 15–20 分钟，六章约 90–120 分钟。均为制作目标，需试玩校准。
- 课堂适配：剧情可回顾、可暂停；不强制实时倒计时。教师可进入指定订单，不要求先完成整个经营主线。

## 二、玩家的一天

```text
开门：看便签、选择今天的备货或整店行动
  ↓
门铃：客户进门，交谈、查看携带的线索
  ↓
工单：确认用途、预算、容量、性能、交期
  ↓
方案：比较真实元件，解释取舍，客户确认报价
  ↓
装机：现有 3D 拖拽、插槽、双内存、接线、检查
  ↓
验机：主机立在桌旁，几秒后显示器出现“开机成功”
  ↓
交付：真实校验、提交回执、客户反馈与剧情选择
  ↓
打烊：结算一次收入、查看关系变化、收到次日线索
```

每次进入营业日只安排一个主要故事客户，另有一条短支线。第一版不做排队压力和同时装三台机器。玩家优先体验“听懂一个人、完成一台电脑”。

## 三、人物设计

所有角色为原创成年人。角色职业只决定故事背景，不直接替代需求调查。人物表现采用半身立绘、少量入场动作和表情切换，避免制作完整人物骨骼与自由行走。

### 立绘与表情标准

- 首批八人各一张标准半身立绘；主要六位客户各三种表情：平静、担忧、满意。老赵增加“认真提醒”，阿岚增加“核对库存”。
- 同一角色保持脸型、发型、服装、配色、道具一致。表情变化不换身份。
- 客户交付满意表现是微笑、放松肩膀；失败表现是担忧和询问原因，避免羞辱玩家。
- 玩家不一定显示立绘。对话框显示“你”的选项，可让学生带入。
- MVP 采用文字与提示音；完整配音是后续可选项目。无配音时允许玩家手动推进，不让自动字幕消失。

## 四、店铺场景

店铺面积设定约 40 平方米，临街玻璃门、整洁但有使用痕迹。外面是社区街道，店内明亮、安静、有人情味。深蓝工作台、浅色墙面、青绿交互提示延续现有系统；木色和暖阳增加生活氛围。

```text
                 后墙：库存架 / 工具墙
     ┌───────────────────────────┐
     │  C 元件库存     B 装机工作台   │
     │                               │
     │  E 公告与照片   D 桌旁验机区   │
     │                               │
     │  A 接待柜台     F 打包交付架   │
     └──────临街窗────入口玻璃门──────┘
```

| 区域 | 画面与可交互物 | 点击后的行为 | 剧情作用 |
| --- | --- | --- | --- |
| A 接待柜台 | 客户、工单夹、柜台便签、门铃 | 与当前客户对话；重看已知需求；确认接单 | 客户进门、交谈、选择方案、接受或延后订单 |
| B 装机工作台 | 防静电垫、工具、未装好的主机 | 进入现有真实 3D 装机；返回店铺时保留装机草稿 | 技术操作主场，不能被“对话答对自动装好”替代 |
| C 元件库存 | CPU/RAM/SSD/GPU 盒、库存夹板 | 查看当前可用元件、下采购单、查看交期 | 缺货与成本取舍；型号仍来自实际元件目录 |
| D 桌旁验机区 | 显示器、键鼠、立式主机 | 进入验机阶段；检查本次真实启动状态 | 数秒等待后显示“开机成功”，随后才可提交交付 |
| E 公告与照片 | 科技节海报、客户便签、合影、次日安排 | 回顾剧情、查看关系反馈和已完成故事 | 让前面的选择有可见痕迹，完成后多一张感谢便签 |
| F 打包交付架 | 当前订单、交付单、纸箱、保修卡 | 展示本次校验回执，客户确认交付 | 结算、感谢或返工分支；未同步显示等待状态 |

### 时间和变化

- 上午：阳光从窗边进来，门牌翻到“营业中”。
- 午后：客户出现，窗外有行人剪影；环境动画不能遮住操作。
- 傍晚：暖色台灯亮起，合上账本，门牌翻到“打烊”。
- 第四日可以是雨天，客户伞放在门口；第六日贴出科技节海报。
- 环境变化服务故事，第一版只做“白天、傍晚”两张背景；雨天与节日由后续迭代增加。
- 店内不设计可随意行走的 3D 人物。用分层场景、点击区域和现有 3D 工作台保证课堂电脑可用。

## 五、章节与订单

六章对应现有六类订单。剧情顺序和教材入口分开：故事模式按营业日推进，课堂练习仍按教材章节进入。

| 日 / 章 | 标题与客户 | 核心技术 | 主要抉择 | 后续回响 |
| --- | --- | --- | --- | --- |
| 1 | 第一声门铃 · 小林 | 用途询问、预算、SSD、核显、基础装机 | 认真问需求；解释经济或均衡方案；遇到未通过就返工 | 小林决定是否向社区推荐；柜台新增首张感谢便签 |
| 2 | 第一台自己的电脑 · 阿宁 | 16GB 内存、学习用途、升级余量 | 钱用在显卡还是实际学习瓶颈；接不接受无必要升级 | 阿宁回来能否自己说出方案理由；科技节志愿者支线 |
| 3 | 参数之外 · 小周 | CPU 与内存平衡、虚拟机需求 | 迎合单一参数偏好，或用工作负载说明取舍 | 小周为科技节带来演示程序；留下“配置说明”作证据 |
| 4 | 留住这些年 · 陈老师 | 大容量存储、容量和速度区别 | 重视资料用途；说明备份需另行确认；避免冒进承诺 | 解锁社区照片墙；为最后的纪录片提供素材 |
| 5 | 少等一会儿 · 小许 | 高速 SSD 与加载瓶颈 | 继续堆容量，或解释速度指标与实际测试 | 小许提供科技节设备清单；实际性能展示仅在测试实现后启用 |
| 6 | 最后一块拼图 · 阿澄 | 32GB、图形加速、2TB 高速存储 | 缺货时协商、等待进货，或诚实不接当前订单 | 阿岚协助供货；成功后阿澄拍下店铺纪录片，进入结局 |

**第六章制作前置条件：**当前元件目录最高存储容量为 1TB，而现有视频订单要求 2TB。必须先实现与真实评估一致的 2TB 元件及采购，或经过明确设计修订支持双盘总容量。前者优先，便于保留单盘安装结构。未完成之前第六章只能进入“缺货协商”，不能假装配置已通过。

### 可见但轻量的支线

1. 老赵工具箱：每日学习一个检查习惯，最后得到工具箱与手写检查单。
2. 阿宁的学习笔记：每次交付请客户复述一个选配理由，解锁公告墙笔记；回答由已发现需求决定。
3. 店铺照片墙：六个客户完成真实交付后留下照片或便签；照片不替代教学得分。
4. 阿岚的周转箱：玩家及时明确采购和交期，供应商在最后一章帮助预留库存。

## 六、第一章完整互动剧本

场景标签：`shop_morning`、`reception`、`workbench_3d`、`test_desk`、`handover`、`shop_evening`。
角色状态：`neutral`、`worried`、`pleased`。下表“下一节点”是可制作的节点 ID，行为由游戏事件执行。

### 方案与接单

| 节点 | 台词、动作 | 选项与结果 |
| --- | --- | --- |
| D1_009 | 展示两条实际方案。经济示例：入门 CPU、8GB 总内存、512GB SSD、核显，当前元件成本 1190。均衡示例：主流 CPU、32GB 总内存、512GB SSD、核显，当前成本 2130。价格必须实时计算，例子不作为固定数值 | “经济方案已经满足这次用途。” → D1_010_E；“多任务更多时，均衡方案有余量。” → D1_010_B；“让我自己选配。” → D1_010_CUSTOM |

### 实操、失败与交付

| 节点 | 触发条件 | 剧情与动作 |
| --- | --- | --- |
| D1_013 | 进入 3D 工作台 | 安装主板、供电、处理器散热器、两条套装内存、存储、必要线缆。保留相机、拖拽、拆装与插槽检查。剧情不替玩家安装 |
| D1_014_FIX | 真实安装或接线检查未通过 | 老赵指出具体缺项：“看一下检查单里标出的连接。”现场高亮相应目标。可继续修正，不进行收入结算、不扣除元件、不复读整段剧情 |
| D1_014_BOOT | 满足启动前置条件并点击开机 | 主机合侧板、立在桌旁；启动等待期间不交付。几秒后，物理显示器显示“开机成功”。动作完成事件驱动 D1_015，不靠台词定时假装成功 |
| D1_015 | 当前配置真实启动成功 | 小林走到验机桌：“这台就是按刚才的用途配的吗？”选“给你看一下工单和验机结果。” → D1_016；选“我还想复检一遍。”可关机再查，清除本次可交付状态 |
| D1_016 | 提交真实订单 | 请求期间显示处理中，禁止重复提交。返回通过且同步成功 → D1_017；配置未达标 → D1_016_REWORK；离线保存 → D1_016_PENDING |
| D1_016_REWORK | 服务端评估未通过 | 小林：“我们把这项再确认一下吧。”展示真实缺口，回选配/装机。返回时如果改硬件，必须重新启动；不结算收入 |
| D1_016_PENDING | 本地记录但未同步 | 显示“本机已记录，等待同步”；客户暂时等候。恢复同步后再结算；不伪造成功，不提前解锁次日 |
| D1_017 | 通过并同步成功 | 小林满意：“谢谢你先问我的用途。明天我不用对着旧电脑干着急了。”展示真实回执与报价，并触发唯一一次交付事件 |
| D1_018 | 交付后选择 | “遇到问题随时回来，我们按工单查。”→ 标记 `offeredAftercare`、小林信任 +1；“这次的配置取舍，我写在说明里了。”→ 标记 `explainedBuild`、小林信任 +1。只能选一次，均不改变教学分数 |
| D1_019 | 打烊 | 老赵：“第一单做完，别忘了记账。今天你最先考虑的是什么？”三个总结选项：用途 / 预算 / 平衡。只改变老赵下一句回应，无隐蔽标准答案 |
| D1_020 | 结算后 | 账本记入一次真实收入与利润，柜台多出小林的感谢便签。次日预告：阿宁发来消息，“我第一次买电脑，能从头给我讲讲吗？”按钮“结束今天 / 回店里看看” |

### 第一章关系结算

- `facts` 三项齐全后接单：小林信任 +1；这是正常流程，每订单仅一次。
- 经济、均衡、自选都可以成为好结局，前提是需求达标、客户确认报价、真实交付完成。
- `rushedPitch` 在正式确认前被补充调查纠正，则只改变一段台词，不永久惩罚新手。
- 选配未达标、装机未通过都进入可恢复返工；技术评分仍由原评估器产生。
- `offeredAftercare` / `explainedBuild` 任选其一：信任 +1，选项不可通过刷新重复刷值。
- 第一章成功交付与关系事件分开：教学过关不是“聊天讨好”，关系高也不能绕过装机。

## 七、选择如何真的影响游戏

第一版只维护三种经营状态，避免整屏指标：店铺现金、店铺口碑、角色信任。

| 情况 | 立即反馈 | 后续影响 |
| --- | --- | --- |
| 把需求问清再推荐 | 工单补全、客户放松 | 相同客户回访时减少重复调查，但新用途仍要重新确认 |
| 解释性能取舍并确认价格 | 客户明确接受经济/均衡/自选 | 交付时评价引用你的解释，公告墙留下对应便签 |
| 缺货时诚实给交期 | 客户可以等、延后或取消 | 阿澄等待分支、供应商预留分支；不强制坏结局 |
| 隐瞒缺项或未经确认擅自升级 | 客户询问、工单缺少确认 | 暂停接单或交付，必须说明与改正；不自动替玩家扣钱 |
| 复检修好问题 | 再次验机，交付状态重新计算 | 好评强调负责，首次修错允许学习，不采用一次失误永久崩盘 |

### 经济与预算口径

- 当前评估器的 `budget` 校验的是元件成本，现有报价公式是 `round(元件成本 × 1.18 + 180)`。第一章台词明确“元件预算 2200，服务另报”，避免把两种价格混为一谈。
- 1190 元示例：报价 1584，现有口径利润 394；均衡 2130 元示例：报价 2693，利润 563。数字均需运行时重算。
- 故事经营的现金不是教学评分。初始资金、房租、采购占款需要经济模拟后确定；MVP 不先加入房租破产压力。
- 第一版采购采用“接单后向供应商订货”的轻经营方式，不同时模拟现货扣款与报价利润，以免双重计成本。
- 扩展实体库存后，采购即扣现金，交付即收报价；账本利润按交付成本确认。该阶段需单独迁移与测试，不沿用简化算法直接重复扣款。
- 取消或延后未采购工单不扣元件。已经采购的可留库存，不把试错设置为现实罚款。
- 结算按稳定 `deliveryId` 去重；刷新、重复响应、重新提交同一订单都不能刷现金、好评和人物信任。

## 八、结局

结局通过“已交付订单 + 经营事件 + 人物信任”确定；不采用隐藏的单一最佳分支。

1. **街坊信任的小店**：六单可靠交付，多位客户形成回访关系。科技节时大家站在店门口，小林贴出社区推荐便签。
2. **认真讲解的工程师店**：完成多次方案解释，阿宁与小周参与讲解。结局场景在公告墙与展示工作台。
3. **准时交付的合作店**：缺货协商与采购安排完成，阿岚、阿澄共同办起展示。结局是供应箱、纪录片和店铺合影。
4. **仍在学习的营业日**：部分订单还未完成，老赵说“店还开着，明天接着做”。允许继续返工补齐，不以失败画面结束教学。

达成多个方向时可展示多个客户留言；玩家选择科技节的店铺介绍语决定结尾重点。不存在必须压预算或必须买最高配置才算成功的暗规则。

## 九、界面与镜头

### 店铺主视图

- 上方仅保留店名、营业日、现金与设置入口。口碑和人物关系放到账本/对话反馈，不常驻一排统计卡。
- 店铺场景占主要面积，人物站在接待区；鼠标悬停只显示“与小林交谈”“进入工作台”等地点提示。
- 下方是对话栏：角色名、最多两行台词、二至三个选项。角色半身立绘可从对话栏侧边延伸进场景，但不遮挡按钮。
- 调查期间用工单夹展示已发现事实；选配与确认报价在柜台旁打开，关闭后仍见到场景。
- 装机时现有 3D 工作台占主要区域，角色只出现在必要提示时；操作按钮和受影响部件同屏。
- 交付时客户与验机桌同框，真实回执出现在主机旁。
- 按 1366×768 普通课堂桌面布局设计；概念探索图为 1440×1024。移动端改为上方场景、下方台词和纵向选项，不直接缩小桌面 UI。

### 有“游戏感”的反馈

- 门铃 → 客户出现 → 目光/表情改变 → 工单写入 → 元件上桌 → 真实启动 → 客户回访。
- 点击地点有轻微高亮；每次选择得到一句具体回应和可见事件，不只更改数字。
- 环境音默认可关闭；首次手势后播放。暂停、离开场景释放声音。
- 对话支持立即显示全文、继续、历史记录；跳过已读剧情仍需本人操作装机。
- 减少动态效果偏好：客户立即出现、直接切场景、启动使用最终姿态但保留验证等待。
- 键盘可遍历热点和对话选项；文字保持真实 DOM，不能把台词烧进背景图片。

## 十、视觉探索方向

将同一场“第一声门铃”制作成三个独立概念，比较空间与对话方式；使用已有工作台截图作为器材与配色参考。人物身份、店名、功能范围保持一致。

| 内部方向名 | 场景组织 | 对话组织 | 制作取舍 |
| --- | --- | --- | --- |
| 温暖街角 | 平视手绘店内，接待柜台近景、工作台与窗户在后方 | 小林较大的半身立绘与底部台词，直接问需求 | 最适合故事代入，场景分层和人物表情成本清楚 |
| 精密日常 | 稍俯视的半写实店内，识别真实工作台、立式主机和元件架 | 客户在柜台旁，对话与工单同时出现 | 延续现有工程气质，重点是场景与 3D 工作台衔接 |
| 街区小店 | 明亮等距店铺剖面，接待、工作台、库存、验机清楚分区 | 点击人物热点进入底部肖像对话 | 经营空间感最强，地点交互自然；需避免热点过小 |

概念图不作为正式分层素材直接切割使用；选择方向后再分别制作背景、人物立绘、表情、环境前景与点击遮罩。不得把已有 3D 元件替换为概念图照片。

## 十二、制作步骤

### 里程碑 A：一个完整可玩的营业日

1. 确定店铺与人物视觉方向，制作首章背景和两位人物的正式素材。
2. 建立剧情节点格式：ID、场景、说话者、表情、文本、条件、选项、事件、下一节点；编写首章上述节点。
3. 制作店铺壳、热点、对话栏、历史记录与工单夹；接上现有元件目录和客户问答。
4. 接入实际选配、装机、开机、服务端回执事件，完成“接待→3D→验机→交付→打烊”。
5. 验证错误安装、未达标配置、断网待同步、修改后重启、刷新恢复、重复结算与键盘操作。

验收：小林以同一角色进入和离开；玩家亲自完成真实装机；回访台词对应选择；交付和现金只发生一次；没有网络也能继续练习但不伪造同步交付。

### 里程碑 B：人物与经营延续

1. 加入阿宁、小周两章及回访，记录不可重复的关系事件。
2. 加入打烊账本和公告墙变化；完善“我的选择产生了后续台词”的反馈。
3. 建立服务端故事进度与经营事件持久化：以用户、存档、订单、事件 ID 隔离，服务端校验来源与金额。
4. 本地可以恢复场景、已读节点、已确认工单和原有装机草稿；启动成功、教学评分和交付结算不能靠本地存档恢复为成功。

### 里程碑 C：六章与科技节

1. 加入陈老师、小许章节；所有速度/性能展示必须有真实测试来源，未实现时只展示现有指标。
2. 实现 2TB 元件、真实配置校验与采购交期后，开放阿澄主线。
3. 加入阿岚供货剧情、科技节结局、角色回访与故事回顾。
4. 教师订单入口与游戏入口共享实际评估器，经营状态单独存储。

### 技术实现边界

- 沿用 React、当前路由、Three.js 与现有 Express 服务，不引入新游戏引擎作为首版前提。
- 建议新模块：`shopStoryData`（原创节点）、`shopStoryEngine`（纯状态推进）、`ShopScene`（背景/热点）、`CharacterDialogue`（人物/台词）、`ShopLedger`（结算）。名字是规划，不表示已生成代码。
- 主状态示例：`scene`, `dayId`, `nodeId`, `activeOrderId`, `facts`, `confirmedQuote`, `relationshipEvents`, `deliveryIds`。
- 工单条件由现有配置与安装状态推导；不同时维护第二套“装好了”布尔值。
- 教学通过、启动有效性由原有逻辑校验；服务端交付成功发出唯一事件后才更新剧情与经营。
- 先用固定原创剧本保障可复现和教学正确性。可选自由输入只作为补充交谈，不能直接改预算、通过状态或结算金额。
- 保留按学生与订单隔离的装机恢复。旧问答状态迁移只影响剧情阅读，不恢复开机和交付。
- 首版只在装机/验机时开启一个 WebGL 场景；在店铺阅读剧情时停止渲染或卸载非必要 3D 资源，回到工作台按已有草稿恢复。

## 十三、验证标准

- 剧情：所有节点/分支能到达操作或结束；未知节点有恢复出口；重复阅读不发重复事件。
- 技术：原有 3D 操作、双内存条、真实接线、桌旁立式启动、关机再修改仍可用。
- 一致性：台词、工单、元件成本、最终报价、服务端结果对应；订单切换没有上位客户残留。
- 存档：换用户不串档；刷新不恢复“已经开机”；离线不显示服务端已接受；重复交付不刷钱。
- 视觉：人物连续性、地点清楚、台词与按钮同屏，1366×768 不需要长距离滚动触发效果。
- 性能：按普通课堂 Windows 10/11、四核、8GB、集成显卡、稳定 Edge 实测。沿用现有生产构建与 3D 包体门槛，新故事图像按场景懒加载。
- 教学：不能用人物好感绕过真实评分；原实验入口、教师指定任务、成绩记录保持可用。
