# 双端架构与游戏化实训平台交付路线图

**日期：** 2026-07-15
**依据规格：** ../specs/2026-07-15-dual-role-architecture-visual-refactor-design.md
**目标设备：** Windows 10/11、四核 x86-64 CPU、8 GB 内存、集成显卡、1366×768、受支持 Edge 稳定版

## 决策规则

出现代码、旧提交、未提交改动、测试和文档不一致时，按以下顺序处理：

1. 用户最近明确批准的决定；
2. 最新设计规格；
3. 当前阶段实施计划与验收测试；
4. 现有代码。

现有代码中符合规格的行为继续保留；与规格冲突的实现可以替换。任何替换必须先记录旧行为，并为仍需保留的能力补回归测试。

## 为什么拆成五份实施计划

该规格同时包含稳定性、前后端架构、学生游戏循环、教师分析和性能质量五个可独立验收的子系统。每份计划必须产生可运行、可测试、可回滚的软件，避免在一个超大提交中同时改变数据、路由、状态和视觉。

## 实施顺序

### 计划 0：稳定性基线

**计划文件：** 2026-07-15-stability-baseline.md

**交付内容：**

- 教师首页不再渲染原始对象；
- AI 测试完全隔离宿主环境和真实网络；
- 课程路线使用真实课程元数据，不显示内部 ID 或负时间；
- 当前实验状态引用和内存访问状态有回归保护；
- 3D 概览、八步组装、部件信息和硬件构建器由隔离 Playwright 流程覆盖；
- 当前工作树中的兼容修复被安全吸收，冲突验证逻辑被替换。

**退出门槛：**

- <code>npm test</code> 零失败；
- <code>npm run build</code> 成功；
- 独立 Chromium 单 worker 双端冒烟通过；
- 3D 验证使用临时数据库，不写入 <code>data/classroom.sqlite</code>；
- 页面无未处理异常。

### 计划 1：共享应用架构

**计划文件：** 2026-07-15-shared-application-architecture.md

**交付内容：**

- <code>App.jsx</code> 只保留启动、会话、角色外壳和顶层通知；
- 建立 auth、student、teacher、domain、shared/ui、shared/api 边界；
- 学生端、教师端、React Flow、Three.js 和教师分析按角色与路由懒加载；
- 后端按 route、service、repository 渐进拆分；
- 保持现有 URL、响应字段和 SQLite 数据兼容。

**进入条件：** 计划 0 全部通过。
**退出门槛：** 双端行为与计划 0 基线一致，入口包不再静态包含 Three.js 和教师分析。

### 计划 2：学生工程解谜核心

**计划文件：** 2026-07-15-student-engineering-game-loop.md

**交付内容：**

- 电路板式学习路线；
- 确定性仿真事件模型；
- 运行、暂停、单步、倍速和首错周期定位；
- 公开样例与隐藏变体判题；
- 快照、撤销、版本和渐进提示；
- 3D 静态降级与键盘等价操作。

**进入条件：** 计划 1 的功能边界和数据契约稳定。
**退出门槛：** 同一输入与方案产生一致轨迹；低配模式仍能完成运行、判题和复盘。

### 计划 3：教师行动与课堂闭环

**计划文件：** 2026-07-15-teacher-classroom-loop.md

**交付内容：**

- 班级健康度、风险学生、共同薄弱点和待办队列；
- 首错类型、卡点热力图和学生操作回放；
- 课堂任务与故障下发；
- 教师关卡编辑器的草稿、预览、发布和版本回退基础；
- AI 助教失败时的本地规则降级。

**进入条件：** 计划 2 提供稳定的仿真事件和学习记录语义。
**退出门槛：** 教师看到的数据可以追溯到学生确定性事件，AI 不可用时核心课堂流程仍可工作。

### 计划 4：性能、可访问性与发布质量

**计划文件：** 2026-07-15-performance-accessibility-release.md

**交付内容：**

- 首屏 JavaScript 和图片预算；
- Three.js 上下文、监听器和计时器释放验证；
- 30 FPS 基线与低性能自动降级；
- 键盘、焦点、对比度和 reduced-motion；
- 双端 Playwright、生产构建和数据库兼容矩阵；
- 课堂部署运行手册与回滚流程。

**进入条件：** 计划 0 至计划 3 全部通过。
**退出门槛：** 满足设计规格中的全部性能、可访问性、兼容性和验收标准。

## 每个计划的统一执行规则

用户已于 2026-07-15 授权实施代码修改。稳定性基线已完成并保留为未提交工作区；以下规则继续约束后续阶段，除非用户另有决定。

1. 每个行为先写失败测试并确认失败原因正确；
2. 只实现让当前测试通过的最小改动；
3. 每个任务结束运行目标测试，再运行完整测试；
4. 每个任务独立审查、独立提交；
5. 不将临时数据库、截图、浏览器缓存或测试输出加入提交；
6. 发现旧代码与最新规格冲突时，不为兼容错误行为而降低规格；
7. 任何 API 或 SQLite 变更必须提供向后兼容验证和回滚说明。
