# 剧情装机店详细制作方案

日期：2026-10-03。用户已授权：先提交并推送当前版本，再写新方案并按方案制作。

## 1. 目标与交付边界

玩家扮演刚接手工作台的装机工程师。通过接待客户、追问需求、选配装机、验机交付完成一张工程委托。第一张办公电脑工单应形成三到五分钟的完整体验；现有六张配置工单均可使用同一流程。教师继续使用现有进度、评分与报告。

本轮交付包括：详细方案、剧情数据与状态规则、客户对话、需求便签、可执行推荐方案、大画面工作台、阶段导航、声音设置、实际结果驱动的交付反馈、继续下一单，以及生产浏览器验证。

后续扩展方向为其他教材章节的工程委托、老客户回访和店铺装饰。本轮不将这些扩展作为完成条件，不新建整站导航或另一套学习记录。

## 3. 玩家流程

### 3.1 接待

默认展示客户身份、订单标题、开场白和三个可追问主题：用途、容量、预算。问题回答来自当前工单真实目标，不隐含评分之外的额外硬件条件。

第一单角色为“小林 / 行政专员”，开场为：“明天要给同事做汇报，想配一台打开表格和资料都利索的电脑。你能帮我看看吗？”

用途回答解释响应速度与存储；容量回答给出内存和资料需求；预算回答说明预算上限。已问问题有明确完成标记，最近一轮回答可重读。

玩家可以快速接单。接单前展示完整目标，保证跳过追问不会遗漏强制要求。对话可以重新打开，已读取线索保存到当前学生、当前订单。

### 3.2 选择方案

提供“经济方案”和“均衡方案”两种推荐。推荐由现有元件价格、性能和工单门槛计算：经济方案选满足要求且总价最低的组合；均衡方案在预算内提高内存、处理器与存储表现。

显示真实成本和配置摘要，玩家点击明确的“采用”按钮才修改选择。两方案确实不同的工单应得到不同配置；无法满足所有目标时说明缺口，不能显示可交付承诺。

第一张办公工单采用经济方案时使用入门 CPU、8GB 内存、512GB SSD 与核显；均衡方案倾向更高 CPU/内存配置。内存组始终对应场景中的两根 DIMM。

### 3.3 装机

接单后收起大段接待内容，保留紧凑客户消息和需求便签。3D 工作台占主要画面，详情订单通过折叠区访问，避免经营卡片压缩操作空间。

保留鼠标拾取与拖放、近景、错误目标、安装/拆卸、两槽卡扣、接线、键盘替代、原教学练习与故障模式。推荐方案只改选择，不自动替玩家安装或接线。

### 3.4 验机

既有装配与接线校验通过才进入自检。主机立放到桌旁，显示器在启动延迟后显示开机成功。关机、配置变动或重新练习立即撤销当前交付资格。

客户跟随状态说话：未开机时提醒进行验机；开机后配置不达标时指出具体缺口；开机且达标时表示可以验收。剧情状态只读取真实工作台状态。

### 3.5 交付与继续

点击交付调用既有成绩提交。提交期间按钮禁用，防止连续点击。交付回执区分“已同步服务器”和“本机已记录、同步待完成”，不将网络失败写成成功同步。

通过时展示客户反馈、当前教学得分、当前报价与利润，允许重看对话或前往下一张工单；未通过时展示原因并提供返回调整。下一单直接使用现有订单选择，不绕过课程的提交前置规则。

不建立独立永久金币账本。经营展示使用现有计算结果，避免刷新或重复提交产生重复奖励。

## 4. 状态与数据

### 4.1 剧情数据

新增 `prototype/src/hardwareStory.js`：客户信息、问题与回答、角色反馈、推荐配置、剧情恢复、阶段推导与交付文案。六张订单共享逻辑、使用各自角色资料。

推荐从 `HARDWARE_PARTS` 全组合计算，所有阈值读取 `HARDWARE_GAME_CASES`。测试验证低价方案、不同路线、不可满足目标和原评分一致性。

### 4.2 状态机

| 阶段 | 条件 | 下一步 |
| --- | --- | --- |
| 接待 | 当前订单尚未接单 | 追问并接单 |
| 装配 | 已接单，本次没有有效开机 | 安装、接线与验机 |
| 验收 | 当前选择已真实开机 | 对照需求，提交方案 |
| 交付结果 | 当前提交回执与订单、配置一致 | 调整或下一单 |

接单、读取线索可恢复。开机、回执、得分、提交状态不进入剧情本地存储。切换用户与订单使用不同键；无 localStorage 时当前流程仍可完成，并提示仅本次页面保留。

配置变化使旧回执失效；异步提交回执只有与提交时订单和配置一致才展示。切订单、退出教学练习、关机都要重新读取实时开机状态。

### 4.3 提交边界

`submitHardwareBuild` 返回提交结果与同步状态；`persistStudentAttempt` 在成功时返回服务端响应，失败沿用现有状态提示并返回空值。其他调用方无需改变流程。

剧情不修改服务器评分标准，不从剧情存储回填学习成绩。课堂任务、提交前置条件和服务端进度响应沿用原路径。

## 5. 界面结构与交互

顶部使用紧凑工单标题、订单编号、阶段条；保留教学练习入口。

接待区采用现有图标库的角色标识、客户名、职业、台词、追问按钮和推荐选项。操作阶段收起成长段文字，需求便签显示预算、CPU、内存、容量、速度与显卡要求。

桌面工作台占主区域。订单、客户便签与经营详情可折叠，保留明确可点击入口。验收按钮与客户反馈同一区域，避免玩家在页面两端寻找结果。

1366×768：压缩顶部装饰，工作台与其主要工具同屏；较小窗口纵向重排。390px：问题按钮和方案纵排，订单可展开，不能横向溢出。

对话回复使用 `aria-live="polite"`；按钮保留可见焦点、键盘操作和状态说明。阶段条使用语义化列表及当前阶段标记，颜色不是唯一状态线索。所有展开区有 `aria-expanded`。

## 6. 动效与声音

沿用现有相机、安装、卡扣和开机动画，不引入额外大型动画库。接待展开与反馈出现使用短 CSS 过渡，尊重减少动画。

声音默认关闭，设置按钮可开启。使用本地 Web Audio 生成短交互音：安装确认、错误、启动、完成。用户开启后才创建音频上下文；切换页面释放资源。音频不可用时操作照常工作。

声音由真实操作回调触发，装配失败不能播放成功音。减少动画与静音分别控制。

剧情修改与基线提交分开。用户的“先提交推送”指当前基线；新制作结果先提供本地预览和验证证据，便于后续单独提交。

## 8. 验收

- 客户身份和对白明确，三个问题可问可重读，答案与当前订单匹配。
- 两种推荐由规则生成，采用后真实选择变化，自动安装数仍为零。
- 接单之后可以完成现有全部装机操作；两根内存、线缆、立放开机正常。
- 没有开机不能交付；关机、改配置、刷新不能恢复交付资格。
- 刷新恢复接单与线索；不同用户与订单不串状态；损坏剧情存储可重新开始。
- 交付结果与实际提交对应；服务器失败可见，不能表现为同步成功。
- 下一单可打开；原教学练习与故障排查仍可进入。
- 桌面和移动无溢出、关键操作同屏，页面没有脚本错误。
- 通过相关 Node 行为测试、生产构建、`qa:production`、剧情浏览器回归与 3D 资源门槛。

## 9. 风险与处理

- **旧 QA 直接操作工作台**：补入接单步骤，其他安装与评分断言保留；不删除保护原功能的检查。
- **恢复与成绩混淆**：存储白名单仅允许接单和问题 ID；回执只存在内存。
- **对话冗长**：每个主题一轮回答、可直接接单，工作阶段默认紧凑显示。
- **数据源漂移**：需求及推荐全部读取原工单数据，文案模板不复制固定评分门槛。
- **异步回执串单**：记录提交时的订单和选择签名，只显示匹配的回执。
- **音频兼容性**：用户手势启动、错误降级、卸载关闭，不影响模型或判分。
